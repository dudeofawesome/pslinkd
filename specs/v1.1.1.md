# V1.1.1 host-only volume mode

V1.1.1 makes a host-only volume approximation the default volume behavior for
the accepted v1.1 button-interaction slice when controls are enabled. It does
not claim to disable or bypass the headset's DSP: no such protocol control has
been demonstrated. Instead, pslinkd keeps the headset's device-side volume at
its maximum level and applies physical volume button presses only to the host
sink.

None of this document is required for v1 or v1.1 completion. V1.2 battery
reporting remains independent of this feature.

## Protocol source and limitation

The device-volume write was independently reverse-engineered and
hardware-tested for the CFI-ZWA2 adapter by
[`Jprnp/pslink-libusb`](https://github.com/Jprnp/pslink-libusb) at commit
`c5dc8061a62a23a077cdc62d3ae83c6dab9bc875`:

```text
SET_REPORT Feature 0xD0, 22 bytes
report[0] = 0xD0
report[1] = 0x02
report[2] = level * 2
all other bytes = 0
```

The device interprets the low five bits of the written `0xD0` byte 2, and the
subsequent `0xB0` `report[44]` readback is `(written_value & 0x1f) >> 1`.
V1.1.1 uses level 15, so the written byte 2 is `0x1e`. The source project
validated this on firmware 1.43; pslinkd MUST validate it on the Olympus
CFI-ZWA2 running firmware 1.38 before release.

This write changes the active DSP volume. There is no evidence that it is
persistent across power cycles or that any known report disables the DSP volume
stage. A physical button press can therefore change device gain briefly before
pslinkd observes the report and restores level 15. Documentation and logs MUST
describe the feature as an approximation and MUST NOT call it a hardware or DSP
bypass.

## Configuration

V1.1.1 adds strict YAML key `controls.volume_mode` and Home Manager option
`services.pslinkd.controls.volumeMode`. Both are enums with these values:

| Value | Behavior |
| --- | --- |
| `synchronized` | Existing v1.1 absolute `report[44] / 15` host-volume convergence |
| `host-only` | Fixed device volume 15 plus relative host-volume button actions |

The default is `host-only`. This intentionally changes the behavior of a v1.1
configuration that enables controls but omits `volume_mode`; users who want the
v1.1 behavior MUST select `synchronized` explicitly. The selected mode is inert
while `controls.enabled` is false; decoding and event logging remain
unconditional. V1.1.1 does not add a configurable device target, host step,
per-button mapping, or event hook.

## HID feature writing

The HID layer MUST support `HIDIOCSFEATURE(22)` on the already selected
read/write interface-3 hidraw descriptor. The ioctl request number MUST be
computed using the Linux `_IOC` layout for the build architecture rather than
copied as an architecture-specific literal.

The write MUST use the exact 22-byte `0xD0` payload above. It MUST NOT use
libusb, detach a kernel driver, read the interrupt stream, or consume endpoint
`0x81`. Writes MUST be cancellable by shutdown and invalidated by disconnect,
adapter removal, or selected-adapter replacement. Expected device errors use
the existing quiet disconnect classification; unexpected failures and recovery
use rate-limited structured HID logging and identify report `0xD0`. A feature
write failure MUST NOT itself advance radio-link debouncing or change routing;
the normal `0xB0` reads remain authoritative for connection state.

## Device-volume convergence

While controls are enabled, volume mode is `host-only`, and the headset is
connected, device volume 15 is desired:

- the first valid connected report with any other valid volume MUST request
  one `0xD0` write;
- every later valid report below 15 MUST request or retain the same desired
  write;
- a valid report at 15 confirms convergence;
- repeated reports at 15 MUST NOT produce writes; and
- invalid or absent volume state MUST NOT be treated as confirmation and MUST
  NOT be replaced with a guessed value.

Writes use the existing desired-action revision, finite timeout, and bounded
retry behavior. Equivalent pending restores MUST be coalesced. A successful
ioctl followed by a valid report below 15 remains unconverged and is retried;
the daemon MUST avoid a tight write loop while waiting for the next poll.
Confirmation at 15 MUST emit one `device_volume_restored` record for that
restore cycle. Repeated confirmations MUST NOT repeat the record.

Device-volume convergence stops immediately on disconnect or removal and
restarts from fresh state after reconnect. It MUST NOT change the host sink
volume merely because the daemon starts, reconnects, restores device volume,
or observes an absolute-volume report.

## Host button behavior

In `host-only` mode, each normalized volume-up or volume-down rising edge MUST
request exactly one host step of `1 / 15`. Volume-up adds the step and
volume-down subtracts it. The resulting scalar is clamped to `0..1`.
Simultaneous independent up and down edges are both consumed and produce a net
zero pending change.

The controller MUST resolve the current headset sink and read its current
volume before deriving the first pending target. It MUST then issue an absolute
`wpctl set-volume` target so retries are idempotent; blindly retrying a relative
`N%+` or `N%-` command is forbidden. Additional button edges received while a
target is pending MUST be accumulated against that pending target, clamped to
`0..1`, rather than lost or based on a stale host read. Once no target is
pending, the next edge starts with a fresh host-volume read so user changes made
through another audio client are respected.

Sink resolution, subprocess timeout, desired-action revision, bounded retry,
and obsolete-action cancellation follow v1.1. A host-volume read or write
failure MUST NOT stall HID polling or device-volume restoration. Button-edge
history retains the v1.1 rules: a held bit produces one action, and connect or
replacement establishes a baseline without synthesizing a press.

Absolute volume changes in `report[44]` continue to produce normalized logs but
MUST NOT set host volume in `host-only` mode. Microphone button and mute
convergence behavior is unchanged from v1.1.

## Automated acceptance

Tests MUST cover:

- strict config and Home Manager `host-only` defaults, accepted enum values,
  and rejection of unknown values;
- explicitly selected `synchronized` behavior matching v1.1 and no writes or
  host actions while controls are disabled;
- portable `HIDIOCSFEATURE(22)` construction and the exact 22-byte level-15
  payload;
- one initial restore below 15, confirmation at 15, no repeated writes at 15,
  coalescing, retry after failed/unconfirmed writes, and cancellation on
  disconnect, removal, replacement, and shutdown;
- no device write for an invalid or unavailable absolute volume;
- exactly one `1 / 15` host step per independent rising edge, both directions,
  clamping at 0 and 1, simultaneous-edge cancellation, and no repeat while
  held;
- a fresh resolved sink-volume read for the first edge, absolute idempotent
  writes on retries, accumulation of edges while pending, and a fresh read
  after pending work completes;
- no host-volume action for startup, reconnect, device restore, or a raw
  absolute-volume change without a button edge;
- continued normalized absolute-volume logging in `host-only` mode;
- independent retry/failure behavior for host-volume and device-volume work;
- one `device_volume_restored` record per restore cycle, without repeats after
  convergence; and
- unchanged v1.1 microphone convergence.

## Olympus v1.1.1 release gates

Before v1.1.1 is complete on firmware 1.38:

1. Capture the `HIDIOCSFEATURE` transfer and confirm the exact `0xD0`, mask
   `0x02`, value `0x1e` payload restores `report[44]` to 15.
2. Confirm the write affects active headset gain, determine whether it survives
   power-off/reconnect, and document the observation without assuming
   persistence.
3. With host volume at several starting levels, press volume up and down and
   confirm each press changes only the settled host volume by one fifteenth
   while device volume returns to 15.
4. Measure and record the duration and audibility of the temporary device-side
   gain change between a physical press and restoration. If the transient is
   operationally disruptive, v1.1.1 MUST NOT be released as host-only volume.
5. Validate lower and upper host-volume clamping, rapid alternating presses,
   held buttons, daemon restart, reconnect, adapter removal, and write failure
   recovery without duplicate host steps.
6. Change host volume through another audio client between button presses and
   confirm the next press uses that current value rather than overwriting it
   with stale daemon state.
7. Play sustained audio while repeatedly pressing both volume buttons; feature
   writes and polling MUST NOT destabilize USB audio, PipeWire, or the adapter.
