# V1.2 battery reporting

V1.2 is a battery-observability slice layered on the accepted v1 routing
daemon. It does not depend on the v1.1 button and control slice, and neither
v1 nor v1.1 completion depends on it.

## Protocol source and scope

The battery protocol was independently reverse-engineered and hardware-tested
for the CFI-ZWA2 adapter by
[`Jprnp/pslink-libusb`](https://github.com/Jprnp/pslink-libusb) at commit
`c5dc8061a62a23a077cdc62d3ae83c6dab9bc875`: feature report `0x82`, byte 3,
contains a battery level on a `0..15` scale. That project calibrated the scale
against the percentage displayed by Sony's application on firmware 1.43.

pslinkd MUST validate the same mapping on the Olympus CFI-ZWA2 running firmware
1.38 before releasing v1.2. V1.2 does not add support for `054c:0fa3` or any
other adapter profile.

## HID polling and decoding

While the debounced radio link is connected, the daemon MUST read feature
report `0x82` through `HIDIOCGFEATURE(64)` on the selected interface-3 hidraw
device. Byte zero MUST be initialized to `0x82`. This is an endpoint-0 control
request; battery reporting MUST NOT read or otherwise consume interrupt
endpoint `0x81`.

The first battery request MUST be made promptly after a transition to connected.
Later requests MUST occur every five seconds while connected. The interval is
fixed and is not configurable in v1.2. Battery polling stops while disconnected
or the adapter is absent, and restarts with an immediate request after the next
connection.

A valid response is exactly 64 bytes, has report ID `0x82` in byte zero, and has
`report[3]` in `0..15`. The normalized battery state contains:

| Field | Value |
| --- | --- |
| `battery_level` | the exact integer from `report[3]`, in `0..15` |
| `battery_percent` | `battery_level * 100 / 15`, rounded to the nearest integer |

The percentage sequence is therefore `0, 7, 13, 20, 27, 33, 40, 47, 53, 60,
67, 73, 80, 87, 93, 100`. The daemon MUST NOT imply finer precision than this
discrete scale.

Wrong report IDs, wrong lengths, and values above 15 are invalid battery
samples. Battery read or decode failures MUST NOT count as radio-link failures,
change routing, close an otherwise healthy reader, or terminate the daemon. An
unexpected failure MUST use the existing rate-limited HID failure and recovery
logging behavior while identifying report `0x82`; expected device errors remain
quiet. A failed sample does not erase the last valid value while the same
headset remains connected.

Battery state becomes unknown immediately on radio disconnection, adapter
removal, or selected-adapter replacement. Values from an earlier connection or
device MUST NOT be reported after a reconnect until a new valid `0x82` response
arrives.

## Reporting

The first valid battery sample after each connection and every later change in
`battery_level` MUST emit one `headset_battery_changed` JSON record. The record
MUST contain `battery_level` and `battery_percent` in addition to the common log
fields. Repeated samples at the same level MUST NOT emit another change record.

If a known battery value is cleared by disconnection, removal, or replacement,
the daemon MUST emit one `headset_battery_unavailable` record. Starting without
a known value MUST NOT emit an unavailable record.

V1.2 exposes battery state through structured logs only. Desktop battery
integration through UPower, a D-Bus or socket API, notifications, battery-based
actions, charging-state decoding, time-remaining estimates, and low-battery
threshold configuration require separate specifications and are not part of
v1.2.

## Automated acceptance

Tests MUST cover:

- feature request `0x82` using a 64-byte buffer initialized with the report ID;
- all raw levels `0..15` and the exact percentage sequence above;
- rejection of a wrong report ID, wrong length, and raw values above 15;
- an immediate first request after connection and five-second periodic requests;
- no battery requests while disconnected or the adapter is absent;
- one change event for the first valid value and each changed level, with no
  repeats for an unchanged level;
- clearing and re-reading state across disconnect, removal, and selected-device
  replacement;
- battery read/decode failures leaving connection debouncing and audio routing
  unchanged;
- expected versus unexpected battery-read logging and recovery; and
- prompt shutdown or device removal while a battery ioctl is in progress.

## Olympus v1.2 release gates

Before v1.2 is complete on firmware 1.38:

1. Capture report `0x82` at several charge levels, including near empty and
   full, and confirm byte 3 remains in `0..15` and tracks the headset indicator.
2. Confirm the percentage mapping against any battery percentage Sony exposes;
   otherwise record that the percentage is a linear presentation of the raw
   15-step scale rather than a vendor-calibrated percentage on firmware 1.38.
3. Confirm power-off, reconnect, adapter removal, and adapter replacement clear
   stale battery state and reacquire a fresh value.
4. Observe the report while charging and fully charged. Record any additional
   stable charging-state field for a future specification; v1.2 MUST NOT infer
   charging state from battery level movement alone.
5. Play sustained audio while polling both `0xB0` and `0x82`; monitoring MUST
   NOT destabilize USB audio, PipeWire, or the adapter.
